Práctica 3: Programación dinámica — ConstellationNet

Nesta práctica (2 semanas) traballaremos cunha rede de satélites chamada ConstellationNet. Un vehículo de mantemento debe saír dun satélite, visitar todos os demais exactamente unha vez e regresar ao punto de partida. O obxectivo é atopar o ciclo de menor custo: o Problema do Viaxante (TSP).

Implementaredes dúas solucións exactas, unha por forza bruta e outra mediante programación dinámica, integradas nun intérprete de comandos. Non se trata de executar Dijkstra entre dous satélites: agora hai que visitar todos os nodos do problema e volver á orixe.

Primeira parte: modelo de dominio e datos

data.json contén os datos de 12 satélites. Contén un array de obxectos cos campos name, agency, orbit_type, launch_year, x, y, z, transmitter_power_w, status e description. Os nomes son únicos e as coordenadas son números finitos en km respecto ao centro terrestre. Os datos son didácticos: as posicións considéranse fixas durante toda a execución.

Para dous satélites distintos A e B, o custo é:

custo(A, B) = math.ceil(A.distance(B))
custo(A, A) = 0

Node.distance calcula a distancia euclidiana 3D. Redondéase cara arriba cada salto antes de sumar os custos, non a suma final. O resultado é un número enteiro de unidades de custo (quilómetros redondeados); non se imprime como float. Dous satélites diferentes na mesma posición poden ter custo 0.

Nesta práctica o grafo é completo e simétrico: sempre se pode viaxar directamente entre dous satélites. O alcance e a potencia de transmisión non interveñen no cálculo dos custos.

Problem ordena os satélites polo seu nome e proporciona names (tupla de nomes), costs (matriz de enteiros) e index(name). Cada índice identifica a mesma fila, columna e nome. Os algoritmos deben funcionar con outros ficheiros do mesmo formato, sen codificar nomes nin respostas de exemplo.

Segunda parte: forza bruta e programación dinámica

Implementade os métodos seguintes:

  • Solver.brute_force(origin): enumerar todos os posibles percorridos dos nodos distintos da orixe, calcular o custo completo incluíndo o regreso e escoller o mellor.
  • Solver.dynamic(origin): resolver o mesmo problema empregando programación dinámica. Non se esixe un algoritmo concreto.

Ambos devolven (cost, route), onde cost é un enteiro e route unha tupla de nomes coa orixe ao principio e ao final. Nun problema con n nodos, a ruta ten n + 1 nomes. Cada nodo distinto da orixe aparece exactamente unha vez. Cun único nodo, o resultado é (0, (origin, origin)).

Desempate obrigatorio: se varias rutas teñen o mesmo custo mínimo, escollede a lexicograficamente menor.

As dúas implementacións deben resolver correctamente cada comando, tamén cando se cambia de problema ou de orixe.

Terceira parte: intérprete de comandos e contrato de saída

O intérprete le un ficheiro UTF-8 liña a liña. Ignora liñas baleiras e liñas cuxo primeiro carácter non branco sexa #. Non se admiten comentarios ao final dun comando. Usa shlex.split: os nomes e rutas con espazos deben ir entre comiñas. Os comandos e os modos non distinguen maiúsculas de minúsculas; os nomes dos satélites si.

As rutas relativas de LOAD resólvense respecto á carpeta do ficheiro .input. Por exemplo, desde examples/TEST1.input, LOAD square.json busca o JSON en examples/ e LOAD ../data.json búscao na raíz do proxecto. As rutas absolutas úsanse directamente. Ao ler comandos de stdin (-), as rutas parten do directorio de traballo. Non hai menú interactivo nin chamadas a input().

LOAD <ficheiro_json> [n]

Carga o JSON e substitúe por completo o problema anterior. Se se indica n, selecciona os primeiros n rexistros na orde do ficheiro. n é un enteiro entre 0 e o número de rexistros, ambos incluídos. Sen n, carga todos os rexistros. Non se acumulan nodos entre chamadas.

Imprime exactamente unha liña:

PROBLEM LOADED WITH <n> NODES

Exemplos: LOAD data.json 6, LOAD "examples/data with spaces.json" 3.

TSP <orixe> <BRUTE_FORCE|DYNAMIC>

Executa o algoritmo indicado sobre todos os nodos do problema cargado. O modo é obrigatorio; non hai selección automática segundo o tamaño. Exemplos:

TSP ISS BRUTE_FORCE
TSP ISS DYNAMIC
TSP "James Webb" DYNAMIC

Se hai resultado, imprime exactamente unha liña:

TSP <MODE>: <ruta_JSON> WITH COST <cost>

MODE imprímese en maiúsculas. ruta_JSON é un array JSON de cadeas, producido por json.dumps(list(route), ensure_ascii=False): comiñas dobres, un espazo tras cada coma, caracteres Unicode sen escapar e escapes JSON cando cumpran. cost é un enteiro decimal sen separadores, decimais nin unidades. O comando fornecido encárgase desta serialización.

Exemplo completo

O ficheiro examples/square.json contén Base=(0,0,0), A=(3,0,0), B=(3,4,0) e C=(0,4,0), co mesmo esquema de satélites. Para esta entrada:

LOAD square.json
TSP Base BRUTE_FORCE
TSP Base DYNAMIC

A saída exacta é:

PROBLEM LOADED WITH 4 NODES
TSP BRUTE_FORCE: ["Base", "A", "B", "C", "Base"] WITH COST 14
TSP DYNAMIC: ["Base", "A", "B", "C", "Base"] WITH COST 14

O ciclo inverso tamén custa 14, pero escóllese o que visita A antes de C polo desempate lexicográfico.

Execución e corrección automática

Desde a raíz do proxecto:

uv sync --locked
uv run tsp examples/TEST1.input

Tamén se admiten as formas:

uv run python -m tsp.interpreter examples/TEST1.input
uv run python src/tsp/interpreter.py examples/TEST1.input
printf 'LOAD data.json 1\n' | uv run tsp -

O corrector executará uv run tsp <ficheiro.input> e comparará stdout co ficheiro .output esperado. Cada comando produce unha liña, rematada en salto de liña, sen espazos finais nin liñas baleiras adicionais. Non imprimades mensaxes de depuración, menús, tempos nin resultados intermedios desde os algoritmos. Con entrada válida, o código de saída é 0 e stderr queda baleiro por defecto.

Os erros de sintaxe, número de argumentos, modo, lectura ou formato de datos interrompen a execución con código 1 e un diagnóstico en stderr co prefixo [LINE <n>] ERROR:. O texto posterior depende do erro e non forma parte da comparación de resultados. Se non se pode abrir o script, úsase a liña 0. As saídas de comandos anteriores ao erro consérvanse. Os erros dos argumentos da CLI son os de argparse (código 2). Os tests de resultados empregarán datos e comandos válidos, incluídos os tres casos especiais anteriores.

Os ficheiros examples/TEST*.input e examples/TEST*.output son pares de entrada/saída. Unha vez completados os algoritmos, podedes comprobar cada par así:

uv run tsp examples/TEST1.input > actual.output
diff -u examples/TEST1.output actual.output

O esqueleto sen completar informa de NotImplementedError mediante o diagnóstico de erro e remata con código 1 cando chega a un TSP que require resolver un problema. Os exemplos describen o comportamento esperado da implementación completada.

Medición de tempos

Para comparar os algoritmos sen alterar stdout:

uv run tsp --time examples/TEST1.input > actual.output 2> tempos.txt

Con --time, cada resolución correcta engade a stderr unha liña TIME <MODE>: <segundos> s, con seis decimais. Mídese só a chamada ao algoritmo; estes valores son variables e non se comparan no corrector. As mensaxes especiais non xeran tempos.

Para observar a diferenza de rendemento, podedes comparar ambos algoritmos con 4, 6 e 8 nodos e ampliar só a versión dinámica ata os 12 nodos. A forza bruta con 12 nodos explora 11! = 39.916.800 permutacións. Non é necesario executala con ese tamaño. A corrección de forza bruta usará ata 8 nodos e a de programación dinámica ata 12.

Normas de entrega

  1. Entregade un ficheiro Apelidos_Nome.zip.
  2. Na raíz do ZIP deben estar pyproject.toml, uv.lock, README.md, data.json, src/ e examples/. Conservade a estrutura e as sinaturas proporcionadas.
  3. Excluíde .venv, .git, __pycache__, ficheiros temporais, resultados locais.
  4. As entregas noutro formato comprimido, cun nome incorrecto ou cunha estrutura incompatible co comando de avaliación serán cualificadas cun 0.

A corrección comprobará o resultado e o formato con entradas non publicadas, e revisarase que cada método implemente a técnica solicitada. Unha saída correcta obtida codificando as respostas ou usando o mesmo algoritmo nos dous métodos non cumpre os requisitos.
